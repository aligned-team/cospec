# Design

## Context

Every fact below was read from the pinned `@fission-ai/openspec` 1.13.1 dist
under `apps/cli/node_modules/@fission-ai/openspec/dist/` (paths in this document
are relative to it) or probed by running the pinned binary, or cospec at
`origin/main` (v0.9.0), under a sandboxed
`HOME`/`XDG_*`/`CODEX_HOME`/`USERPROFILE`/`ZDOTDIR` below
`/var/folders/tn/_13rsr_n2r10v3s97ms94_xw0000gn/T/claude-501/`. Where the binary
and the roadmap disagree, the binary wins and the entry says so.

**What cospec does today.**

- Twelve canon bodies in `canon/workflows/*.md`, paired with each selected
  harness row by `renderHarnessFiles` (`harness/render.ts`). Its pipeline per
  workflow is: read the raw body, replace `{{TYPE_TABLE}}` when the manifest
  says `injectTypeTable`, then `transformBody` for the row's dialect. Canon
  files resolve through `canonFile()` (`canon/embedded.ts`), whose registry is
  explicit so the standalone compiled binary can read them; an unregistered file
  throws.
- Root grounding is ad hoc. Only `propose` runs `cospec context --json` and
  stops on an unresolved root; `explore` lists the same command as a read-only
  tool; `apply`, `archive`, `sync-specs`, `verify`, `update`, `continue` and
  `ff` each carry their own "select the change" paragraph; `new`, `onboard` and
  `bulk-archive` carry none of it. No body distinguishes a workflow the agent
  chose from one the user asked for.
- `ApplyInstructionsJson` (`core/openspec.ts`) has no `context`,
  `operationGuidance` or `references`, yet `cospec apply --json` already carries
  all three at runtime: `relayApplyInstructions` spreads the parsed document
  (`...instr`), so the keys ride along untyped, `references[].fetch` unspelled.
  Probed: in a sandbox project whose `config.yaml` holds `context:` and
  `operations.apply.guidance`, `cospec apply <change> --json` printed both in
  `apply`. The human transcript prints neither, in either path (the clear-gate
  path and `applyLegacy`).
- `cospec instructions archive --change <id> --json` already works.
  `instructions` deliberately does not alias `archive` to `cospec archive`: it
  forwards upstream's read-only lookup. Probed against the same project it
  prints `{changeName, context, operationGuidance, root}`.
- `cospec list --json` carries the binary's `lastModified` and its default
  recent-first order (`--sort name` is forwarded), plus `type`, `gate` and
  `state`. With no root it exits 1 with `root: null` and one `status`
  diagnostic, and with a declared but unresolvable store that diagnostic's
  `message` starts `Declared in <path>/openspec/config.yaml:` (probed for an
  unknown store, code `no_registered_stores`, and a malformed id, code
  `invalid_store_id`).
- The tasks artifact's text is `canon/artifacts/tasks/meta.yaml`, composed into
  all eleven types' schemas (`openspec/schemas/**`, regenerated by
  `mise run generate`) and goldens (`test/unit/schemas/golden/*.schema.yaml`).
- `harness-render.test.ts` holds byte goldens of every shipped row's render.
  This change moves them on purpose.

**What the binary does** (the contract this change ports):

- `core/templates/workflows/project-root.js` `PROJECT_ROOT_GUARD`: three
  paragraphs. Run the list command (`--store <id>` when a store is selected) and
  read `root`; `"root": null` means not set up. One `null` is not about setup:
  when a `status` error message starts `Declared in` or
  `Invalid store declaration in` and names this project's `openspec/config.yaml`
  (or `config.yml`), the project uses a store this machine cannot resolve, so
  stop and show that error's `message` and `fix`. Otherwise **Auto-selected**
  (the agent chose the workflow itself): stop using the tool and answer
  normally, mention no setup. **Explicit request** (the user named the tool or
  the skill, or ran its command): stop before writing and ask how to proceed.
  Both branches: never create the root as a side effect.
- `continue-change.js:29-37` and `update-change.js:44-52` (the only two
  templates with it): when ambiguous, run the list command sorted by most
  recently modified, present the top 3-4 as options showing the name, schema,
  status and how recently modified (the `lastModified` field), and mark the most
  recent `(Recommended)`.
- `propose.js:117-123` and `ff-change.js:72-75, 190-193` (skill and command
  surface each): "Inspect the relevant project before drafting", three bullets.
  `continue-change.js` does not carry it.
- `explore.js:57, 108-109, 439-440`: the Visual bullet and "Draw with plain
  ASCII only".
- `apply-change.js` (steps 3-4) and `core/project-config.js`
  `loadOperationInputs`: `context` is a required prompt-level input,
  `operationGuidance` optional additive advice, both kept apart from
  CLI-returned state. `OPERATION_IDS = ['apply', 'archive']`.
- `archive-change.js:36-64` and `bulk-archive-change.js:48-72`: the advisory
  `instructions archive --change "<name>" --json` lookup, optional and
  non-blocking, with its own precedence paragraph. The bulk form runs it once
  for the batch.
- `bulk-archive-change.js:100-165`: a conflict is two or more selected changes
  with a delta for the exact same `<capability-path>`; the agent reads each
  delta, searches the codebase for implementation evidence, and records an
  include or exclude decision per delta (only one implemented: that one; both:
  chronological order, newer overwrites; neither: skip and warn), with a
  rationale.
- `commands/workflow/instructions.js` `printApplyInstructionsText` and
  `printOperationInputsText`: the human transcript prints a
  `### Referenced Stores` section, then at the end
  `### Project Context (required instruction input)` (verbatim) and
  `### Operation Guidance (advisory)` (each entry through `sanitizeInline`), or
  `No project context or operation guidance configured.` when neither exists.

## Goals / Non-Goals

**Goals:**

- Each of the six ported passages reaches the cospec bodies in cospec's own
  vocabulary, with no bare `openspec` command, and every ported passage records
  where it came from.
- `operations.apply.guidance` and `operations.archive.guidance` reach an agent
  that follows `apply.md` or `archive.md` alone.
- One declaration of the root-grounding text, rendered into every body.
- No default-config user sees any `cospec apply` output change, and nothing but
  the twelve bodies and the tasks guidance moves in generated files.

**Non-Goals:**

- Porting the rest of upstream's templates (its store-selection paragraph,
  `instructions specs` snapshots in bulk archive, the targets the roadmap rows
  do not name). Each is a row of the full inventory or of no row; this change
  owns rows 62-67 and the defects named in D7 and D11.
- A new validation rule for archive rows in `tasks.md` (D11 records why).
- Profile or delivery behaviour, which is `workflow-profiles`.
- Running an eval or a benchmark. Both need keys this project keeps human-held,
  so no `@eval` or `@benchmark` row is planned (D13).

## Decisions

### D1. What `workflow-profiles` provides, and what this change assumes of it

This change is authored against `main` at v0.9.0, where `workflow-profiles`
(R12) has not merged. The implement stage rebases onto it
(`blocking-changes.md`, task 1.2). R12's `design.md` (D6, D7) says it will add:

- `harness/optional-workflow.ts`, with
  `resolveOptionalWorkflows(text, installed)`, run in `renderHarnessFiles` on
  the **raw canon body, before `{{TYPE_TABLE}}` injection and before
  `transformBody`**.
- The markers `[[opsx:if-workflow <id>]]`, `[[opsx:else]]`, `[[opsx:end]]`, and
  the rewrite of every `/cospec:<id>` in the twelve bodies into one, on one line
  wherever it sits in a table row or bullet.
- `core: true` on six entries of `harness.yaml`.
- A canon unit test that fails on any `/cospec:<id>` outside a conditional
  branch, any marker id outside the manifest, and any fallback naming
  `/cospec:`.

What this change builds on that:

- **Order.** Fragment interpolation is the first step of the render pipeline,
  before R12's resolver, so the resolver and the canon test read the final text.
  The fragment has no `/cospec:<id>` and no marker, and `_shared/root-guard.md`
  is itself scanned by the canon test.
- **New body text.** Every `/cospec:<id>` in this change's new or reworded body
  text (the handoffs in `archive.md`, `bulk-archive.md`, `apply.md`) is written
  in R12's wrapped form from the start. Until R12 is on the branch, the existing
  unwrapped references stay as they are. The rebase reconciles every body line
  both changes touch; task 1.2 records what moved.
- **`harness.yaml`.** R12 adds `core: true`; this change adds `ported:`. Both
  are per-workflow keys and conflict only textually.
- **`render.ts`.** R12 adds `workflows` and `delivery` options and the resolver
  call; this change adds `interpolateFragments` and its call one step earlier.

If R12's merged code differs from its design, the rebase follows the code and
task 1.2 says so.

### D3. The shared fragment

`canon/workflows/_shared/root-guard.md` is the one text of the three parts
below. `render.ts` gains `interpolateFragments(body, read)`, which replaces each
registered token with the fragment's text, and a registry of one entry:

```
FRAGMENTS = { '{{ROOT_GUARD}}': '_shared/root-guard.md' }
```

The token follows `{{TYPE_TABLE}}`'s shape. Every one of the twelve bodies
carries exactly one `{{ROOT_GUARD}}`, placed after its opening paragraph and
before its first step, so the guard precedes anything that writes. A body that
lacks the token, carries two, or carries any other `{{NAME}}` token that is not
`{{TYPE_TABLE}}` makes the render throw, and the canon unit test asserts it for
all twelve. The read goes through `canonFile('workflows/_shared/root-guard.md')`
(a new `embedded.ts` entry, so the compiled binary has it) or
`join(canonDir, '_shared/root-guard.md')` under the existing `canonDir`
override. The fragment is dialect-neutral text, so `transformBody` runs over it
with the rest of the body and no body-side rewriting is needed.

The fragment's three parts, the roadmap's, in cospec's vocabulary. Upstream's
constant opens with a lead-in check that parts 1 and 2 both read, so the
fragment opens with it too:

- **Lead-in: the check.** Before the first step that writes anything
  (`cospec new`, `cospec archive`, `cospec sync-specs`, or authoring an artifact
  file), run `cospec list --json` (with `--store <id>` when a store is selected)
  and read `root`. A root object means set up. `"root": null` with exit 1 is
  that answer, not a broken CLI: read the JSON, do not retry. A write such as
  `cospec new` would create `openspec/` as a side effect.
- **Part 1. The auto-selected versus explicit branch.** With no root:
  **auto-selected** (the agent chose this workflow itself, without the user
  naming cospec, the skill or its command) means stop using cospec, answer the
  request as with no cospec installed, and say nothing about setup; **explicit
  request** means stop before writing and ask whether to set the project up
  (`cospec init`), target a store they already have (`--store <id>`), or
  continue without cospec for this request, then wait. Both: never create the
  root as a side effect, never run `cospec init` until the user asks, never
  hand-create `openspec/` files.
- **Part 2. The store-declaration carve-out**, which takes precedence over part
  1. One `"root": null` is not about setup: when a `status` entry's `message`
     starts `Declared in` or `Invalid store declaration in` and names this
     project's `openspec/config.yaml` (or `config.yml`), the project does use
     cospec through a store this machine cannot resolve. Do not treat it as
     uninitialised and do not take either branch of part 1: stop before writing
     and show that entry's `message` and `fix`. Both prefixes are the binary's
     (`core/root-selection.js:199, 220`); cospec relays them (probed above), so
     the fragment names them verbatim.
- **Part 3. The recency-ranked change picker** (D4).

**Replaced prose (T7).** Each body's own grounding is replaced, not stacked.
`propose` step 1 keeps `cospec context --json` and `root.path` as the
authoritative root (the living `harness-workflows` spec requires that), and
delegates its stop-on-no-root text to the fragment; its current "ask the user
how they want to proceed" sentence is the explicit branch, so this changes
behaviour only for an auto-selected `propose` (D12 amends the spec). The "Select
the change" paragraph of `apply`, `archive`, `sync-specs`, `verify`, `update`,
`continue` and `ff` keeps its sole-change auto-select and `Using change: <slug>`
announcement (the living spec requires both) and points to the fragment's picker
for the ambiguous case. `explore` keeps `cospec context --json` as a tool and
loses nothing else.

**Rejected: split the fragment** into a root-check fragment and a picker
fragment, so `propose`, `new`, `onboard` and `explore` skip the picker. The
roadmap's acceptance bullet is one fragment in all twelve, a body that never
selects a change reads the picker paragraph as inert (it opens "When a step asks
you to choose among changes"), and two tokens would let a body drop the check.
**Rejected: inline interpolation in `harness.yaml`** (as `injectTypeTable` does
per workflow): every body needs it, so a per-workflow flag only lets one be
forgotten.

### D4. The change picker, as cospec's list reports it

The picker paragraph ports `continue-change.js:29-37` onto cospec's list: when a
step has to choose among several plausible changes, run `cospec list --json` and
use its order (recent first by default, which the binary defines and cospec
forwards), present the top 3-4 as options, each with its name, `type`, `gate`
state and task progress, and how recently it was modified from `lastModified`,
mark the first `(Recommended)`, and never pass `--sort name`. The roadmap's
phrase "3-4 most recently modified" is the binary's; cospec adds `type` and
`gate`, which the bodies already show ("each change's type and gate state").
`bulk-archive` is the one body that does not use it: it never auto-selects and
lets the user multi-select, as the living spec requires.

### D5. `propose` and `ff` inspect before drafting (T2)

Both bodies gain the three-bullet passage of `propose.js:117-123`, placed in
their artifact loop between re-reading dependencies and writing: read `context`
and `rules` from `cospec instructions ... --json` first (never by opening
`config.yaml`; the living spec forbids it), then inspect the implementation,
nearby tests, configuration and documentation **outside `openspec/`**, read-only
and in proportion to the change; identify the target project from the request
and the context, and **ask when it is unclear**; ground scope, approach and
tasks in what was found, distinguishing observed behaviour from assumptions and
surfacing conflicts with existing specs; do that discovery now rather than
leaving "explore the codebase" tasks.

The passage reconciles with two existing sentences. `propose` and `ff` say "you
do not need to explore the repo to learn what to write... do NOT read
`openspec/schemas/`, `openspec/config.yaml`, or other repo files to
reverse-engineer an artifact's shape". That sentence is about the artifact's
_format_, which `cospec instructions` owns and still does; the new passage is
about the _subject matter_ the artifact describes. Both stay, and the old
sentence is reworded to say which is which, so neither reads as contradicting
the other. `continue` has the same format sentence and, as upstream's
`continue-change.js` has no inspection passage, gains none.

### D6. `explore` draws ASCII only (T3)

Port `explore.js:57, 108-109`: a Visual bullet in the stance list ("use ASCII
diagrams when they clarify thinking") and a paragraph "Draw with plain ASCII
only: borders `+` `-` `|`, arrows `-->` `<--` `^` `v`, markers `*` `x`. Unicode
diagram glyphs can render at different widths across terminals, fonts and
locales, so padded boxes and aligned tables can drift. Keep every diagram
character ASCII." It scopes to diagram characters: the body's own prose keeps
its punctuation. A canon test rejects any box-drawing or arrow glyph (U+2190
-U+21FF, U+2500-U+257F) in the rendered `explore` body, so the passage cannot be
followed by an example that breaks it.

### D7. `cospec apply` shows the project's inputs (T4)

- **Types.** `ApplyInstructionsJson` gains `context?: string`,
  `operationGuidance?: string[]` and `references?: ReferenceEntry[]`, the shape
  `dist/core/references.js` fills and `instructions-render.ts` already models.
  `ReferenceEntry` is exported from `instructions-render.ts` for it.
- **Spelling.** `relayApplyInstructions` additionally spells the command fields
  of `references` with `respellInstructionsDocument` (`references[].fetch`,
  `references[].status[].fix`, whole-value remedy rule) and nothing else:
  `context` and `operationGuidance` are the user's own text and pass byte for
  byte, including an entry that starts `openspec `. Binary contradicts roadmap:
  the roadmap says `ApplyInstructionsJson` "doesn't declare" these, and that is
  true, but the `--json` path already carries them, so the work there is the
  declaration and the respell (a `references` fetch command printed
  `openspec show ...`); only the human transcript is missing the fields.
- **Human transcript.** `core/operation-inputs.ts` exports
  `renderReferencesSection(instr)` and `renderOperationInputs(instr)`, ports of
  `renderReferencedStoresSection` and `printOperationInputsText` over the
  relayed document. `renderReferencedStoresSection` and `sanitizeInline` are
  exported from `instructions-render.ts`, which already ports the block form and
  the per-entry lines, rather than copied. Both output paths call them: the
  clear-gate path (after the `N of M task(s) remaining.` line and warnings, the
  references section before the instruction, the context and guidance sections
  after it) and `applyLegacy` (same order around its instruction). "Both output
  paths" in the roadmap's acceptance bullet is read as these two, each in text
  and `--json`.
- **Absent means silent.** Upstream prints
  `No project context or operation guidance configured.` when neither exists.
  cospec does not: a repo with nothing configured sees no new line, so default
  output is byte-identical (the first goal). Binary contradicts roadmap only by
  omission; the differential test compares the sections cospec prints with the
  binary's and asserts the absent case prints none.
- **The precedence paragraph.** The roadmap's "the precedence text" for `apply`
  is a paragraph of the **workflow body** (`apply-change.js`, steps 3-4), not of
  the CLI's output, which prints only the two headings. `apply.md` gains it:
  `context` is a required prompt-level input, `operationGuidance` optional
  additive advice, both read from the `apply` object of the
  `cospec apply --json` document; both stay apart from `gate`, tasks, progress,
  `contextFiles` and the built-in instruction; neither is evidence of
  completion, replaces the instruction or lifts a blocked state; a conflict with
  the instruction, an explicit user choice or a CLI-controlled value is reported
  with the controlling value kept, and inapplicable guidance is not followed and
  the reason said; neither is copied into implementation files or planning
  artifacts; both are prompt-level, not enforceable. Acceptance is therefore two
  rows, not one: the CLI output carries the guidance (against the binary) and
  the rendered `apply.md` carries the paragraph (against `apply-change.js`).
- **Un-rowed in the roadmap, owned here by file.** `apply.ts`'s clear-gate
  `--json` document nests the payload as `apply`, so the body reads
  `apply.context` and `apply.operationGuidance`, not top-level keys.

### D8. `archive` and `bulk-archive` consult the project's inputs (T5, T6)

`archive.md` step 1 gains, after the change is selected, the lookup
`cospec instructions archive --change "<slug>" --json` (with the same
`--store`), optional and non-blocking: a non-zero exit or invalid JSON means
continue with no context and no guidance, report nothing, stop for nothing
(`archive-change.js:41-47`). Its precedence paragraph is upstream's
(`archive-change.js:49-60`): `context` is required, `operationGuidance`
additive; neither overrides the built-in steps, explicit user choices, resolved
paths, CLI checks or command contracts; a conflict is reported with the
controlling value kept; no replacement paths, skipped prompts or flags are
inferred; neither is copied into specs, artifacts or the summary; prompt-level
only.

`bulk-archive.md` carries the same lookup **once per batch** (the selected root,
one selected change) with the batch variant of the paragraph
(`bulk-archive-change.js:48-72`). The roadmap's row 66 and T5 name `archive.md`
only; `bulk-archive.md` is this change's T6 file and has the same gap against
the same upstream passage, so it is in scope as an un-rowed defect of a file the
change owns.

Each of the three bodies has its own paragraph rather than a second shared
fragment: upstream's three texts differ in what the controlling inputs are
(`apply` keeps a blocked state, `archive` keeps resolved paths and flags, bulk
keeps the conflict analysis), and one shared text would have to name all of them
in every body. Each is recorded in `ported:` against its own upstream file.

`cospec instructions archive` needs no code change: the lookup is the forwarded
upstream command, and the contract test (verification 2) runs the very line the
rendered body prints.

### D9. `bulk-archive` resolves collisions (T6)

Port `bulk-archive-change.js:100-165` through cospec's primitives, replacing
today's "caught by the later archive's own spec guard; resolve it by editing the
later change's delta".

**Detection.** Binary contradicts roadmap wording: the roadmap says "ADDED
collision"; the binary's conflict is two or more selected changes with a delta
for the exact same `<capability-path>`, whatever the operation. The body detects
at that level (`cospec status --change <slug> --json` names each change's
`artifactPaths.specs`; the requirement names are the `### Requirement:` lines),
because a MODIFIED on both can also overwrite silently. An ADDED of the same
requirement name in both is the case the later `cospec archive` would refuse
(`archive/added-exists`), and the example the body works through.

**Decision.** For each conflicting capability the agent reads each change's
delta, searches the codebase for implementation evidence, and records for each
delta (a change and a `<capability-path>`) include or exclude, with its
rationale and the order: only one change implemented means include that one and
exclude the other; both implemented means include both, **chronological order,
older first** (the change's `created:` in `.openspec.yaml`, ties by slug), with
the newer one overwriting; neither means exclude both and warn.

**Edits.** The resolution edits **only the conflicting change's delta files**,
nothing else: it never writes a main spec (cospec's `archive` does the merge),
never moves a change directory, never touches another artifact. An excluded
delta's colliding requirement blocks are removed from its delta file (the file
goes when no operation is left and the change keeps another delta). An included
newer delta that `ADDED` a requirement an older included delta also adds becomes
a `MODIFIED` of it, carrying the full updated requirement, so the later archive
overwrites instead of refusing. A change that would be left with no deltas where
its type requires specs is reported `Blocked` rather than edited into
invalidity.

**Confirmation.** The resolution table, each proposed edit and the final order
are shown, and **one confirmation covers the batch and the edits**; declined
means nothing is edited and nothing is archived (the living spec's declined
branch). After the edits each edited change must pass
`cospec validate <slug> --strict` before the loop; a failure is that change's
failure and the batch continues.

**Archive.** Each change then goes through `cospec archive <slug>` in the
resolved order (dependency order first, collision order within a capability), so
both hard gates run per change; no `--force*` flag, no hand `mv`.

**Rejected:** porting upstream's agent-driven main-spec merge (`sync` inline).
It would let an agent write main specs and move directories, which the living
spec forbids and which the gates exist to prevent. **Rejected:** a native
`cospec bulk-archive` command; the roadmap scopes this to the body and the
reachability test already resolves upstream's `bulk-archive` workflow through
`aliases.yaml`.

### D10. `ported:` provenance (T7)

`harness.yaml` gains, per workflow, a `ported:` list. `WorkflowDef`
(`harness/adapters.ts`) gains `ported?: PortedPassage[]`, and the manifest
reader validates its shape:

```yaml
ported:
  - passage: root-guard
    file: dist/core/templates/workflows/project-root.js
    pin: 1.13.1
```

`file` is relative to the `@fission-ai/openspec` package root, so a reader sees
the exact template; `pin` is the version it was read at. The entries:

| Workflow        | Passages (upstream file)                                                   |
| --------------- | -------------------------------------------------------------------------- |
| all twelve      | `root-guard` (`project-root.js`), `change-picker` (`continue-change.js`)   |
| `propose`, `ff` | `inspect-before-drafting` (`propose.js`, `ff-change.js`)                   |
| `explore`       | `ascii-diagrams` (`explore.js`)                                            |
| `apply`         | `operation-inputs-precedence` (`apply-change.js`)                          |
| `archive`       | `archive-inputs-lookup` (`archive-change.js`)                              |
| `bulk-archive`  | `archive-inputs-lookup`, `collision-resolution` (`bulk-archive-change.js`) |

`change-picker` is listed for all twelve because the fragment is in all twelve.
The contract test (`test/contract/ported-provenance.test.ts`, or a row of
`operation-guidance.test.ts`) fails when a `file` does not exist in the pinned
dist, when a `pin` is not the pinned version (so a bump lists what to re-diff in
its failure), or when a body that carries a recorded passage's marker sentence
has no entry. The `ported:` key is also read nowhere at render time: it never
reaches a generated file.

### D11. The tasks guidance never produces an archive task (T9)

Binary and roadmap disagree on the premise, and the binary (here, cospec's own
canon) wins: no tasks template **text** contains an archive row. Checked in
`canon/artifacts/tasks/meta.yaml` (`templateBody` and `instruction`), every
`canon/types/*.yaml` note, the generated
`openspec/schemas/*/templates/tasks.md`, and the pinned `spec-driven` schema.
The row appears because the instruction says "Every task states how its own
completion is verified" and the self-hosted flow ends with `cospec archive`, so
an agent writes "archive this change" and verifies it by the archive. That row
cannot be ticked honestly before the archive, and `cospec archive` refuses
incomplete tasks, which is why merge stages have ticked it in the archive commit
or waived the gate.

The fix is in the guidance that produces it. The tasks `instruction` gains a
paragraph: archiving is not a task, because the archive validates the change and
moves it and a task describing it can only be completed by the step that refuses
it while it is open; end the list at the last implementation or documentation
task; where the repo's flow lands the archive as a commit after the last task
(the self-hosted flow does), end that task's description with "The archive
commit follows this one" so it can be ticked before the archive. `templateBody`
is unchanged: it already shows no archive row. The change regenerates the eleven
schemas (`mise run generate`) and the three schema goldens.

**Rejected: a validation rule** (`tasks/archive-row`) that warns on a row whose
text is an imperative to archive. The family has no `tasks/*` rules, the match
is free text, and `validate --strict` fails on warnings, so every false positive
(a task that documents the archive command, as this very change's docs task
does) would block a commit; a new stable rule ID is also public API. The
guidance is the producer, and the unit test (D13) reads it.

### D13. Evidence, and why `agent-behavior` stays unchecked

The prompts change, but their evidence is deterministic: each ported passage is
asserted against the pinned dist's text (a differential test reads the template
file and checks the rendered body carries the same controlling sentences), each
body is asserted by exact render against the goldens, and the behaviours the
prompts describe are driven through the real commands (verification 1, 2, 6). An
`@eval` row would score how a model reads template text this repo already
compares byte for byte, and the eval and bench keys are human-held, so none is
planned and the `agent-behavior` surface is left unchecked, as
`workflow-profiles` does for the same reason. `interactive` and `integration`
are checked, each with the design section its rule requires below.

## Operational surface

The surface is the `cospec apply` transcript and the generated harness files.

- `cospec apply` on a repo with no `context`, no `operations` and no
  `references` prints exactly what it prints today in both paths; with them, it
  prints the sections of D7, after the instruction (context, guidance) or before
  it (references), each only when present.
- `cospec update` rewrites every managed skill and command file once (every body
  changed, so every `contentHash` moved) and reports each as updated.
  `cospec doctor` reports no `stale-harness` for a repo that updated. No flag,
  no exit code and no `--json` key is added.
- A body that is a few kilobytes longer: the fragment adds roughly 2 KB to each
  of twelve skills. Skills load on demand, and commands are the same body.
- `apply --json`'s `apply.references[].fetch` and `.status[].fix` read
  `cospec ...` (the narrow BREAKING item of the proposal).

## Integration contract

The third-party contract is the pinned binary's documents and templates.

- `instructions apply --change <id> --json` (and cospec's relay): keys
  `context?: string`, `operationGuidance?: string[]`,
  `references?: {store_id, root?, specs?, fetch?, status[]}[]`, each present
  only when set (`...operationInputs`, `...(references !== undefined ...)`).
  Operation ids are `OPERATION_IDS = ['apply', 'archive']`; an unknown id, a
  non-object, an unknown field or a non-array `guidance` makes the binary print
  a `console.warn` line from its config load and drop the entry, which reaches
  cospec's stderr as the binary prints it and is not parsed.
- `instructions archive --change <id> --json`:
  `{changeName, context?, operationGuidance?, root}`.
- `list --json`: `changes[].lastModified` (ISO), recent-first, `root: null` plus
  `status[]` with `code` and `message` when unresolved.
- The template files `ported:` names, in the pinned dist.
- **Fixture shape.** A sandbox project (private HOME/XDG) with an
  `openspec/config.yaml` of `context:`, `operations.apply.guidance` and
  `operations.archive.guidance`, one change with a `tasks.md`; for provenance,
  the pinned package's own dist; for collision, two changes whose deltas ADD the
  same requirement to one capability. The oracle (`upstream-oracle.ts`) runs the
  binary beside cospec on the same fixture.
- **Id-type reconciliation.** A change id is a slug on both sides; a capability
  path is the spec directory relative to `specs/`, preserved whole.

## Risks / Trade-offs

- **R12 rewrites the same lines** -> The implement stage rebases first (task
  1.2), every new body line is written in R12's wrapped form, and the canon test
  scans the fragment and the bodies together.
- **A stale `ported:` pin passes review** -> The contract test fails on a pin
  that is not the pinned version and lists the entries, so a bump cannot skip
  the re-diff.
- **The fragment's auto-selected branch changes `propose`** -> It is the
  upstream behaviour, the amended spec says so, and an explicit
  `/cospec:propose` still reports and asks.
- **A resolution edit corrupts a delta** -> Edits are confined to the changes'
  delta files, are confirmed first, and each edited change passes
  `cospec validate --strict` and both archive hard gates before it moves.
- **The roadmap's "ADDED collision" is narrower than the binary's conflict** ->
  The body detects at the binary's level and the fixture covers the ADDED case
  the archive refuses.
- **The guidance fix does not stop an agent from writing the row** -> It removes
  the instruction that produced it and states the rule; the unit test pins that
  text. A row written anyway is the user's flow, not the template's.
- **Every managed file changes on update** -> It is one regeneration, and the
  proposal says so.
