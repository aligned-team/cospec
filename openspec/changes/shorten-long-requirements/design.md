# Design

## Context (root cause)

The 1.15.0 parity change adds a `requirement-too-long` rule that matches
OpenSpec 1.14.1: a requirement description over 500 characters is an error.
Descriptions here are measured as the text between the requirement heading and
its first scenario, stripped. This repo's living specs have many requirements
over that limit, and `cospec validate --all --strict` runs in the pre-commit
hook and CI, so the rule cannot land until the specs are under it. PR #100
shortened every over-limit requirement it touched, some of them together with a
behaviour change.

The change sits directly on `main`, beneath `change-stamp-x-prefix`. It is a
`fix` rather than a `refactor` because the refactor schema allows only `RENAMED`
spec deltas, while a fix may carry `MODIFIED` ones when the living spec itself
was wrong, which an over-limit requirement is.

## Goals / Non-Goals

**Goals:**

- Land pr-100's editorial rewording of the living requirements, and only that,
  so the parity change's spec deltas are the behaviour changes and nothing else.
- Keep every obligation and every scenario the living text carries.

**Non-Goals:**

- Any code, test, docs-site or generated-file change.
- Shortening a requirement whose wording #100 changed together with behaviour.
  Those belong to the change that owns the behaviour.
- Fixing the spec gaps #100 inherited ("Shared .agents/skills harness root",
  "Delivery selects the surface a workflow is written to"). They are carried as
  pr-100 wrote them and the parity change amends them.

## Decisions

- **Per-requirement classification, not per-capability.** Each of the 151
  requirements #100 modified in these capabilities was diffed against main and
  classified editorial or behavioural; the manifest records the justification.
  Only the editorial ones are here. Alternative rejected: moving whole
  capabilities, which would drag behaviour-coupled wording into a change that
  claims none.
- **Text is pr-100's, verbatim, generated by script.** Each delta is the full
  block (heading, description, every scenario) from pr-100's living spec, in the
  living spec's order. Alternative rejected: re-shortening the requirements
  independently, which would make this change and the parity change disagree and
  leave the end state different from #100's.
- **No composition.** All 151 blocks are pr-100's text with no hand edits, so
  the end state matches #100's. `change-stamp-x-prefix` applies its stamp
  corrections on top of these texts.
- **Behaviour-coupled rewordings stay with their owners.** A requirement whose
  text #100 changed together with behaviour is shortened by the change that
  changes the behaviour, so each such change's delta shows the behaviour and the
  shortening in one reviewable place and this change never describes behaviour
  the code does not yet have.
- **Clauses dropped are listed, not hidden.** The proposal's "Clauses removed"
  section names every condensation that lost prose a reviewer might call an
  obligation, so it can be objected to before merge.

## Risks / Trade-offs

- [A condensation silently drops an obligation] ->
  `archive/scenario-preservation` refuses a block that drops a scenario, and the
  proposal lists the clauses removed and the largest condensations for review.
- [A block drifts from pr-100] -> the verification ledger re-runs the
  requirement diff against pr-100 and expects every block identical.
- [A requirement still over 500 characters surprises the parity change] -> the
  ledger counts the living requirements still over the limit and checks that
  they are all owned by the parity change.

## Seam ownership

This change owns nothing at runtime: it edits living-spec text only. The shared
state it touches is `openspec/specs/**` wording. The parity change owns the
requirements whose wording changed with behaviour (and amends the two inherited
gaps noted above), and this change owns the editorial rewording of the rest.
