## Context

The compiled binary already self-spawns as bun (`BUN_BE_BUN=1`) to run wrapped
openspec, but only ever resolves openspec from a project `node_modules`
(`Bun.resolveSync('@fission-ai/openspec/package.json', base)` over
`import.meta.dir`, `execPath` dir, `cwd`). A `mise use github:…` install has
none of those, so wrapped calls fail with a "npm i -D @fission-ai/openspec"
caveat. openspec 1.5.0 bundles cleanly with `bun build --target=bun` (564
modules, 2.9 MB / 1.8 MB minified), with one runtime obstacle: four
`createRequire(import.meta.url)('../../package.json')` reads (one at module
load) that bun leaves as runtime requires. Its built-in `schemas/` are resolved
from `import.meta.url` too, but cospec always composes project-local schemas at
`init`, so resolution step 1 (project-local) always wins — empirically verified:
`new change`, `validate`, `status`, `instructions apply` all succeed against the
bundle with no built-in schemas on disk.

## Goals / Non-Goals

**Goals:**

- A `mise`/GitHub-release install runs every wrapped call with no
  `node_modules`, no bun, no npm — no extra install step.
- Preserve today's behavior for project installs (their in-range openspec is
  used) and for `bun run` dev/contract tests.
- Preserve wrapped-call discipline (version assertion, exit codes, stdout
  deny-list, observable post-conditions).

**Non-Goals:**

- Embedding openspec's built-in `schemas/` (unnecessary — cospec writes
  project-local schemas at init; the fallback path is unreachable in a
  cospec-managed project).
- Changing the pinned openspec version or the accepted range.
- Bundling once per platform — the bundle is platform-independent JS, produced
  once and embedded into every platform binary.

## Decisions

- **Single-file bundle embedded via `{ type: 'file' }`, not a vendored package
  tree.** Rejected: embedding openspec's whole `dist/` + `schemas/` (hundreds of
  files, unenumerable statically) or an embedded tarball (needs a tar extractor
  bun lacks cross-platform). One bundle is one static import, mirroring the
  canon embed pattern, and `bun build --compile` proved to embed a `.js` asset
  as bytes in `$bunfs` and self-spawn it via `BUN_BE_BUN=1`.

- **Extraction layout satisfies openspec's runtime relative reads.** The four
  `../../package.json` reads (relative to the single bundle file) are satisfied
  by extracting the bundle to
  `<cache>/cospec/openspec-<ver>/vendor/bin/openspec.js` and synthesizing
  `<cache>/cospec/openspec-<ver>/package.json` (2 levels up) carrying the pinned
  version. No package.json is embedded — the version is a known constant.
  Rejected: patching the bundle to inline the version (fragile string surgery on
  third-party output).

- **Resolution order: in-range `node_modules` copy, else embedded.** Only the
  previously-throwing "not found" path changes to the embedded fallback; a
  resolvable project copy still runs through the existing version assertion
  (out-of-range still refuses unless drift is overridden). This keeps every
  contract-tested semantic for project installs and adds the embedded path only
  where there was an error before.

- **Committed, drift-gated vendored bundle.** The static import must exist on
  disk at both `bun run` (dev module-load) and `--compile` time, so the bundle
  is generated by a `vendor:openspec` task and committed like other generated
  managed files, with a `--check` drift gate in `mise run check`. Rejected:
  generating at build time only (breaks `bun run` module load, since the import
  target would be missing in dev/CI).

- **Extraction is write-once with an atomic rename + byte-length
  post-condition.** Concurrent cospec invocations may race the first extraction;
  writing to a temp file and `rename`-ing into place makes the published path
  always a complete file, and the post-condition (exists + byte length equals
  the embedded source) is the wrapped-call observable for the extraction step.

## Risks / Trade-offs

- [openspec bumps its runtime asset layout (e.g. reads `../../package.json` from
  a different depth, or hard-requires built-in schemas)] → The pin is
  load-bearing and already gated: bumping openspec runs the contract suite and
  re-probes; the vendored-bundle drift gate forces a rebuild, and the standalone
  integration test exercises the embedded path end to end, so a layout change
  surfaces as a red gate, not a silent break.

- [Repo carries a ~1.8 MB generated JS blob] → Accepted: it changes only on an
  openspec pin bump, is excluded from lint/format/tsc, and is the price of a
  genuinely self-contained binary. Minified to roughly halve it.

- [Built-in schema fallback is unreachable, so a non-cospec/legacy schema in a
  standalone install resolves to `unknown`] → Out of scope: cospec's remit is
  cospec-typed projects, which always have project-local schemas; the existing
  `resolveSchema` try/catch already degrades to `unknown` gracefully.

## Operational surface

- **Artifact topology:** one platform-independent openspec bundle
  (`apps/cli/src/vendor/openspec.bundle.js.tpl`, minified) is generated once at
  build time and embedded into all seven per-platform compiled binaries; the
  release build matrix is unchanged (no per-leg bundle step).
- **Runtime extraction target:**
  `${XDG_CACHE_HOME:-~/.cache}/cospec/openspec-<version>/` — write-once, atomic
  rename; created on first embedded wrapped call. No network, no elevated
  permissions; needs a writable cache dir (falls back to `~/.cache`).
- **Child process:** the embedded bundle runs as
  `process.execPath <bundle> --no-color …` with `BUN_BE_BUN=1`, `NO_COLOR=1` —
  same spawn contract as the node_modules path.
- **Binary versions/arches:** wrapped openspec is pinned to 1.5.0 (accepted
  range `>=1.0.0 <2.0.0`); the embedded copy is by construction the pin.
  Compiled binaries: darwin x64/arm64, linux x64/arm64 (gnu + musl), win32 x64 —
  all embed the same JS bundle.
- **Required secrets / bind address / connection limits:** none — no network
  listener, no secrets; extraction and spawn are local filesystem only.
